nocturne but better 2.6.2 - package verification
checked september 25, 2026 on windows 11, using windows powershell 5.1.

installer
81 checks ran against throwaway copies of the game files. the
real game folder was not used, and its files were unchanged afterwards.
- every package script parses in windows powershell 5.1.
- install previews (-whatif) leave the game folder unchanged for both
  loaders, and so does the uninstall preview.
- a game without melonloader gets the bundled bepinex and the plugin. a
  repeat install changes nothing.
- upgrading from the published 2.1.2, 2.2.0, 2.4.1, 2.5.0, 2.6.0, or 2.6.1
  plugin installs 2.6.2 and keeps the old dll as a backup. upgrading the
  2.2.0, 2.4.1, 2.5.0, 2.6.0, or 2.6.1 melonloader mod does the same.
- finding the game without being told where: fake steam folders (never
  the real registry) list a library on a missing drive, an offline network
  share, folders that are gone, names with [brackets], spaces and letters
  like ü, steam's old library format, and locked or unreadable steam files.
  each finds exactly the one test game, and an install and uninstall work
  that way. these checks fail on 2.6.1's installer, which stopped with
  "cannot find drive" or missed the library. the fullscreen fix script
  gets the same lookup checks.
- install.cmd and uninstall.cmd work from a folder with [brackets], an
  apostrophe, unicode, & and %.
- with melonloader 0.7.3 installed and turned on, the mod goes into mods and
  the bepinex copy is disabled. a melonloader-only game gets no bepinex
  files. a repeat install changes nothing.
- after melonloader is removed, running the installer again brings back the
  bepinex plugin and disables the mods copy. only one copy is ever enabled.
- a melonloader that is turned off in userdata\loader.cfg, or whose proxy
  dll is missing, leaves bepinex in charge.
- a stray folder on the unused loader's path doesn't block the other loader.
- uninstall disables every enabled copy for both loaders, keeps the loaders,
  and repeats cleanly. declining its confirmation is reported as incomplete.
- the installer refuses these without changing any file: an unknown dll in
  either mod location, a corrupt payload, melonloader older than 0.7.3, a
  melonloader 0.5 layout, bepinex beside an enabled melonloader, melonloader
  when it isn't installed or won't start, a different steam build, an
  unknown game asset, a conflicting loader binary, and a disabled doorstop
  configuration. an existing compatible doorstop configuration is kept.

for 2.6.2 the installer's steam lookup was rewritten, and the real
installer upgraded the test pc's own game from 2.6.1 to 2.6.2. the optional fullscreen script got the same lookup fixes. neither
script touches the custom charts or custom battles folders.

shareable dlls
- both are built from the 2.6.2 source with debug symbols disabled and no
  git commit hash, so they contain no development-machine paths.
- this package's source folder, built with -c Release, gave the same
  bytes as the shipped dlls. the bytes depend on the files' line endings,
  so build from the folder as it is, without converting them.
- the source folder has all of the mod's code, including art\ and audio\.
  2.6.0's left those two folders out, so it didn't build.

gameplay coverage
both loaders were tested in-game with qa builds: the same source plus test
hooks, on nocturne 1.0.1 with bepinex 6.0.0-be.788 and melonloader 0.7.3,
the melonloader one in a separate copy of the game folder. every run took
a snapshot of the player's plugin, settings and saves first, put that
snapshot back afterwards, and checked that the .sav files hadn't changed.
on melonloader, no run logged a "native->managed trampoline" error.
for 2.6.2 (steady frames on real battles; stutters in a model):
- two 4-lane custom battles on mp3 songs, each played twice on bepinex,
  one with 169 speed changes and its first note at 0:00, the other with
  an #offset: the notes started 2.02 s and 0.61 s before the song, and
  the start logs showed steady frames (the longest 35 ms) and the song
  and notes within 30 ms of each other.
- the stutter tests (250 and 700 ms frames forced at the start) ran on
  2.6.1: the notes lurched to 1.3 to 2.3 times their speed for a moment,
  on the game's own firefly song too. 2.6.2's change was checked against
  a model of the game's clock with the same stutters, not in the game.
- not tried in the game: the creator's new "tempo change here" on a new
  battle, and 2.6.2 on melonloader (its code changes are the same for
  both loaders, and no new game hooks were added).
for 2.6.1 (each fix with a test through the player's own path, also run on
the old code first to show it catches the bug; both loaders unless noted):
- pause-menu quit: 5 fights in a row, paused the way esc does and left
  with the pause menu's exit button (one through its gameplay page). every
  later fight had music and moving notes, and no options error was
  logged. 2.6.0 failed at the second fight (no music).
- timing, speed mod 170, 2d upscroll: steady note speed from the start;
  in battles with #offset -2, -1.53, -0.2 (and +0.5 s on bepinex) the
  first note came within 5 ms of where the chart editor puts it (2.6.0
  ignored the offset, so its notes were that far off).
  a first note at 0.2 s got a 1.32 s lead-in. bepinex also in 3d.
- enemy attack opacity 50%: 12 of 12 attacks after a custom enemy's
  health hit 0 faded (0 of 12 with 2.6.0's code); a game fight's death
  still played before the results.
- custom enemy art, 10 battles: defeat only when the enemy died at the end.
- again from 2.6.0: set gear 228 of 228, level 233 of 233, dialogue in the
  arcade, and the chart editor's test (6 runs on bepinex, 2 on
  melonloader). bepinex also: the creator's .osz import (every check), the
